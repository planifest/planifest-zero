# ADR-002 - Setup cleans up telemetry wiring on every run

**Skill:** [adr-agent](../../../.claude/skills/planifest-adr-agent/SKILL.md)
**Feature:** 0000033-remove-telemetry-mcp
**Component:** planifest-zero
**Date:** 2026-09-10

## Context

A project that ran `setup.sh --structured-telemetry-mcp` before this feature has telemetry wiring on
disk. Its `.claude/settings.json` names hook commands pointing into `.claude/hooks/telemetry/`, and
names the matcher `mcp__structured-telemetry-mcp__emit_event`. It has a `.claude/telemetry-enabled`
sentinel, and it may have `plan/.telemetry-failures/` or `plan/.telemetry-receipts/` directories.

ADR-001 deletes the modules those entries point at. That makes this case different from an ordinary
stale file. The entries are not inert. The tool reads `.claude/settings.json` and tries to run the
named command on every prompt, so a missing module produces a failure on every turn. Three of the
four Scope Lock drafts identified this independently as the most likely failure.

Today's code already filters telemetry entries out of the settings array before rebuilding it, at
three points in `setup.sh` and one in `setup.ps1`. Those filters live inside the telemetry functions
this feature deletes. Removing them without replacement would strand the broken entries permanently,
because setup would no longer know they exist.

Feature 0000032 ADR 003 set this framework's precedent for its own stale output: remove the exact
path after a successful write, print one line, warn without failing.

## Decision

1. On every setup run, remove telemetry hook entries from the project's `.claude/settings.json`,
   identified by their command string referencing the telemetry hook modules or by the
   `mcp__structured-telemetry-mcp__emit_event` matcher.
2. Delete `.claude/telemetry-enabled` if present.
3. Delete `plan/.telemetry-failures/` and `plan/.telemetry-receipts/` if present.
4. Print one line per removal. On failure, print one warning, leave the item alone, and continue.
   Setup still exits zero.
5. Print nothing when there is nothing to remove. A second run is silent, which makes an upgraded
   project indistinguishable from a fresh install.
6. Run the cleanup on every invocation, not behind a flag or a version check. Setup is already
   idempotent, and a flag would require the person to know they once enabled telemetry.

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Leave the wiring in place and document it | Setup never touches a file it did not write this run | The tool tries to run a deleted module on every prompt, in every upgraded project, for ever. The person sees an error with no stated cause | The entries are broken references, not inert leftovers |
| A pending migration file the migrator skill walks the human through | Human confirms each removal | Asks a person to approve deleting entries that setup itself wrote and that are already broken, and leaves them broken until the next orchestrator session | The same reasoning that rejected a migration in 0000032 ADR 003 |
| Print a warning naming the stale entries and let the person remove them | No deletion inside a file the person may have edited | Every upgraded project gets a manual step, and the settings file is generated by setup in the first place | Setup owns those entries, so setup should retract them |
| Clean up only when the old sentinel is present | Narrower trigger | A project whose sentinel was deleted by hand still has broken settings entries, and would never be cleaned | The sentinel is not a reliable signal of what is in the settings file |

## Affected Components

| Component | Impact |
|-----------|--------|
| planifest-zero (`setup.sh`) | Gains a cleanup step that runs on every invocation, replacing the filters lost with the deleted telemetry functions |
| planifest-zero (`setup.ps1`) | Gains the mirror of that step, with the same printed wording |
| planifest-zero (tests) | New cases: wiring present then gone, second run silent, unwritable settings file warns and continues |

## Consequences

**Positive:**
- An upgraded project is repaired by the same command that upgrades it, with no manual step and no separate migration.
- After one run, an upgraded project and a fresh install are indistinguishable on disk.

**Negative:**
- Setup now edits entries in `.claude/settings.json` that it did not write during this run, which is a wider claim over that file than it made before. The claim is limited to entries matching the telemetry commands setup itself once wrote.
- The cleanup code outlives its usefulness. Once no project in the world has telemetry wiring, it is dead weight that still runs on every invocation.

**Risks:**
- A person who hand-added their own hook whose command string happens to reference the telemetry module paths would have it removed. This is unlikely, because those paths point at modules the framework no longer ships.
